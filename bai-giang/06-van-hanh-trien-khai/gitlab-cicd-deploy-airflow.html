01 Hai khái niệm dễ nhầm: DAG vs Pipeline

Cả hai đều là "đồ thị có hướng không chu trình", nhưng theo quy ước ngành chúng không gọi chung tên.

DAG

thuộc Airflow

Cỗ máy giao hàng

Pipeline

thuộc GitLab CI/CD

Nội dung file .gitlab-ci.yml — các stage và job lo việc kiểm thử, đóng gói và mang DAG đi deploy.

Gọi nội dung .gitlab-ci.yml là "DAG" thì người trong nghề sẽ không hiểu. File yml đó chính là pipeline, chứ không phải "chứa" pipeline bên trong.

03 "Push image lên đâu?" → Container Registry

Máy build (Runner) và máy chạy (server production) là hai máy khác nhau — cần một kho trung gian.

Image được build trong môi trường mà Runner dùng để thực hiện job. Sau khi job kết thúc, môi trường tạm đó thường bị dọn dẹp (đặc biệt với shared runner hoặc Kubernetes runner) — nên nếu không docker push image lên Container Registry thì image sẽ không còn để các máy khác (hoặc production) tải về. Hình dung Registry như "GitHub cho image"; GitLab tặng sẵn mỗi project một cái miễn phí.

Runner · build ──push──▶ Container Registry ──pull──▶ Server · chạy

04 Tại sao mỗi bước tồn tại

Phần cốt lõi để hiểu, không chỉ để làm theo.

lint+test trướcMột DAG lỗi có thể làm hỏng việc parse cả các DAG khác. Chặn code lỗi ngay từ cổng.
build imageDAG phụ thuộc môi trường (duckdb, extension postgres, module pipeline/). Đóng gói tất cả → chạy ở đâu cũng giống hệt. Hết "works on my machine".
tag = commitTag image bằng mã commit để rollback: lỗi thì trỏ lại tag cũ, quay về trạng thái cũ trong 30 giây.
deploy manualDelivery = người bấm nút deploy (an toàn cho người mới). Deployment = merge vào main là tự động deploy. Chọn bằng một dòng when: manual.
bí mậtSSH key & mật khẩu không để trong .gitlab-ci.yml — đặt ở Settings → CI/CD → Variables, Runner nhận qua biến môi trường lúc chạy.

05 Bộ file của nghiên cứu này

Ba file thật đã soạn trong project, sẵn để anh lead đọc code.

FileNội dung
.gitlab-ci.ymlPipeline hoàn chỉnh: lint → test → build → deploy, comment từng phần.
docker-compose.prod.ymlCompose bản production: pull image từ registry, tách init / scheduler / webserver.
RESEARCH_gitlab_cicd_airflow.mdTài liệu nghiên cứu dạng văn bản (bản đầy đủ của trang này).
Khác biệt dev vs prod: bản dev dùng build: + command: standalone (gộp mọi process, password random — chỉ để dev). Bản prod pull image từ registry và tách rõ init + scheduler + webserver.

06 Muốn chạy thật thì cần gì

Tầng 3 — chưa làm theo yêu cầu "đừng tạo repo vội". Checklist cho bước tiếp theo.

  • Tạo repo GitLab (hoặc mirror repo GitHub hiện tại sang).
  • Có ít nhất 1 GitLab Runner (GitLab.com có shared runner miễn phí).
  • Bật Container Registry cho project (mặc định đã bật).
  • Khai CI/CD Variables: SSH_PRIVATE_KEY (File), DEPLOY_HOST, DEPLOY_USER, POSTGRES_PASSWORD, AIRFLOW_ADMIN_PASSWORD.
  • Một server production có docker + docker compose, chứa docker-compose.prod.yml + .env.
  • Kiểm tra cú pháp .gitlab-ci.yml bằng công cụ CI Lint của GitLab — không cần chạy pipeline.
